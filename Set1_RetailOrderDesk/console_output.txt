--- Analysis & Explanation of Observed Differences ---
1. Complexity Difference: Linear Search has O(n) complexity. With n = 50,000 records,
   it requires on average n/2 = 25,000 comparisons and 50,000 comparisons in the worst case.
2. Logarithmic Scalability: Binary Search has O(log2 n) complexity. For n = 50,000,
   ceil(log2(50,000)) = 16 comparisons maximum. It eliminates half of the remaining space
   at every step, resulting in a dramatic orders-of-magnitude performance improvement.
3. Hardware & Memory: Sequential memory traversal in linear search experiences cache line
   benefits but is completely overshadowed by 25,000 pointer dereferences versus only ~15 for binary search.
4. Precondition: Binary search requires sorted data (O(n log n) one-time cost). In a high-read
   support desk scenario where orders are queried tens of thousands of times, pre-sorting or indexing
   by Order ID pays for itself almost immediately.

--- Complexity & Data Structure Rationale ---
1. Time Complexity: O(n) average.
   - Each order is visited exactly once.
   - Hashing the composite key (Customer ID + 2-decimal Amount + Minute bucket)
     and inserting into the HashMap takes O(1) amortized time.
   - Contrast with Naive Nested Loop Comparison: O(n^2). For 50,000 records,
     naive requires n*(n-1)/2 = 1,249,975,000 comparisons (several minutes).
     The hash-based structure completes in just ~296 ms!
2. Space Complexity: O(n).
   - HashMap holds at most n entries, consuming O(n) auxiliary memory.
   - In an enterprise retail system with 50,000 orders/day, ~50,000 map references
     occupy less than 5 MB of RAM, representing an outstanding trade-off for real-time speed.

--- Architectural Comparison & Takeaways ---
1. Stack Implementation:
   - CustomStack uses dynamic array resizing with geometric growth, giving O(1) amortized push/pop.
   - Java's legacy `java.util.Stack` inherits from `Vector` where every method is synchronized.
     This synchronization adds unnecessary lock contention and performance overhead in single-threaded tasks.
   - `ArrayDeque` is the recommended modern replacement for Stack in Java, delivering peak cache locality.
2. Queue Implementation:
   - CustomQueue uses circular modular arithmetic ((tail+1)%length), avoiding O(n) array shift costs.
   - Built-in `ArrayDeque` uses bitwise mask circular buffering (power-of-two capacity), which is ultra-fast.
   - Built-in `LinkedList` allocates a new Node object per enqueue, leading to heavy GC pressure & pointer indirection.

--- Scenario A: Standard Currency System (Greedy Works Optimally) ---
Refund Amount: $3887

  DP Result     : Total: 11 coins/notes [1x$2000 3x$500 1x$200 1x$100 1x$50 1x$20 1x$10 1x$5 1x$2 ]
  Conclusion    : In standard currency, Greedy achieves the provable global optimum.

--- Scenario B: Non-Canonical Denominations (WHERE GREEDY FAILS) ---
Denomination Set: [1, 3, 4]
Target Refund Amount: $6

1. Greedy Step-by-Step Execution:
   - Remaining amount: $6. Largest coin <= 6 is 4. Pick 1x $4. Remaining: $2.
   - Remaining amount: $2. Largest coin <= 2 is 1. Pick 1x $1. Remaining: $1.
   - Remaining amount: $1. Largest coin <= 1 is 1. Pick 1x $1. Remaining: $0.
   => GREEDY RESULT: 3 coins [4, 1, 1]

2. Dynamic Programming Optimal Execution:
   - DP explores subproblems: dp[6] = 1 + dp[6 - 3] = 1 + dp[3] = 1 + 1 = 2 coins ($3 + $3).
   => DP OPTIMAL RESULT: 2 coins [3, 3]

+---------------------+-------------------+---------------------+---------------+
| Algorithm           | Coins Used        | Total Coins Count   | Optimality    |
+---------------------+-------------------+---------------------+---------------+
| Greedy Approach     | [4, 1, 1]         | 3                   | SUB-OPTIMAL   |
| Dynamic Programming | [3, 3]            | 2                   | OPTIMAL       |
+---------------------+-------------------+---------------------+---------------+

Additional Counterexample: Denominations [1, 5, 6, 9], Amount = $11:
  Greedy picks: [9, 1, 1] (Total: 3 coins) [Picks 9, then 1, 1]
  DP picks    : [5, 6] (Total: 2 coins) [Picks 6 and 5]

--- Complexity & Algorithmic Rationale ---
1. Greedy Algorithm: Time O(k), Space O(1).
   - Extremely fast and memory-efficient.
   - Only optimal when the denomination system is 'canonical' (satisfies matroid greedy-choice property).
2. Dynamic Programming: Time O(amount * k), Space O(amount).
   - Evaluates overlapping subproblems via optimal substructure.
   - Guaranteed to find the true global minimum for ANY arbitrary set of currency denominations.
